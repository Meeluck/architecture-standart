# Задание 4

Менеджер проектов из команды цифровой трансформации занимается подготовкой дорожной карты проекта. Для этого ему нужно определить, в какой последовательности команды должны делать изменения в своих системах. Понять это поможет архитектура MVP, которую вы спроектировали ранее.

Также команда обнаружила проблему: большинство клиентов банка «Стандарт» — пожилые люди. Как только банк запустит маркетинговую кампанию на текущих и на новых клиентов, количество звонков в кол-центр может увеличиться. Есть риск, что возрастным людям будет непросто сориентироваться в новых процессах и они захотят уточнить условия открытия депозита по телефону.

В ходе анализа проблемы сотрудники банка внесли несколько предложений:

1. Нужно, чтобы сотрудники кол-центра могли проконсультировать клиентов хотя бы по текущим ставкам банка. Для этого надо каким-то образом предоставить их системе доступ к ставкам по депозитам.
2. Есть риск, что кол-центр будет перегружен. Поэтому необходимо подключить к работе партнёрский кол-центр. При этом важно, чтобы сотрудники партнёрского кол-центра также могли проконсультировать клиентов по актуальным депозитным ставкам. Для этого нужно наладить процесс передачи информации об актуальных ставках между банком и кол-центром. Кол-центр партнёра работает во внешней информационной системе относительно банка. Они готовы получать актуальные ставки в виде файлов. Нет возможности сделать API-вызовы (например, через SFTP-протокол).
3. Все эти изменения необходимо учесть в MVP и предложить решение на основе текущего процесса работы со ставками.

### <a name="_qmphm5d6rvi3"></a>**Решение**

#### Логика принятия решений

1. **Один источник актуальных ставок**

   Было важно не допустить появления нескольких независимых каналов получения ставок из АБС. Поэтому новый кейс не создаёт отдельный контур, который напрямую читает модуль управления ставками в АБС, а переиспользует уже выбранный в MVP путь публикации ставок через ABS Integration Adapter.

2. **Переиспользование существующего цифрового контура MVP**

   Так как в предыдущем ADR уже был выбран цифровой контур открытия депозитов с read-model ставок, для нового кейса принято решение расширить *downstream-публикацию* уже получаемых данных, а не строить новый параллельный интеграционный слой.

3. **Изоляция АБС от прямой нагрузки со стороны кол-центров**

   Внутренний и партнёрский кол-центры не должны обращаться напрямую к АБС, так как она уже перегружена и является критичной core-системой. Это позволяет не увеличивать нагрузку на банковский контур и не раскрывать внутренние интерфейсы АБС наружу.

4. **Разделение способов доставки данных по возможностям потребителей**

   Внутренний кол-центр может получать ставки через прикладную интеграцию, поэтому для него используется API / интеграция чтения ставок. Партнёрский кол-центр не готов работать через API и может принимать данные только файлами, поэтому для него выбран файловый экспорт.

5. **Единая read-model для публикации ставок**

   Для публикации ставок используется единая read-model, обновляемая из АБС через ABS Integration Adapter. Это даёт единый опубликованный слой данных для всех потребителей и снижает риск расхождения форматов и бизнес-логики между каналами.

6. **Минимизация объёма новых изменений**

   Для кейса публикации ставок добавляются только те компоненты, которые действительно нужны новому сценарию: API выдачи ставок внутреннему кол-центру, компонент файлового экспорта партнёру и хранение статусов экспорта. Остальная логика MVP открытия депозитов в данный ADR не включается.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

1. **Сделать отдельный независимый контур публикации ставок с прямой интеграцией в АБС**

   Можно было бы реализовать новый сервис публикации ставок, который самостоятельно обращается к модулю управления ставками в АБС. Такой вариант не выбран, потому что он создаёт второй параллельный канал интеграции с АБС, дублирует уже существующую функцию ABS Integration Adapter и увеличивает риск рассинхронизации данных.

2. **Дать внутреннему кол-центру прямой доступ к Rates Read Model**

   Такой вариант технически проще, но не выбран, потому что база данных становится интеграционным контрактом между системами. Это повышает связанность, усложняет эволюцию схемы данных и ухудшает управляемость решения.

**Недостатки, ограничения, риски**

1. **Решение усиливает зависимость нового кейса от уже существующего цифрового контура MVP**

   Публикация ставок в кол-центры теперь опирается на уже принятый поток ставок через ABS Integration Adapter и Rates Read Model. Это упрощает архитектуру в целом, но делает новый кейс зависимым от корректности и доступности существующего цифрового контура.

2. **Есть риск рассинхронизации между модулем управления ставками в АБС, read-model и файлами партнёра**

   Если обновление read-model задержится или файловая выгрузка завершится ошибкой, внутренний и партнёрский кол-центры могут использовать устаревшие ставки.

3. **Файловый обмен с партнёром остаётся технологическим ограничением**

   Отсутствие API у партнёрского кол-центра снижает гибкость интеграции, делает решение чувствительным к формату файла и требует отдельного контроля версии структуры данных.

# Задание 4

Менеджер проектов из команды цифровой трансформации занимается подготовкой дорожной карты проекта. Для этого ему нужно определить, в какой последовательности команды должны делать изменения в своих системах. Понять это поможет архитектура MVP, которую вы спроектировали ранее.

Также команда обнаружила проблему: большинство клиентов банка «Стандарт» — пожилые люди. Как только банк запустит маркетинговую кампанию на текущих и на новых клиентов, количество звонков в кол-центр может увеличиться. Есть риск, что возрастным людям будет непросто сориентироваться в новых процессах и они захотят уточнить условия открытия депозита по телефону.

В ходе анализа проблемы сотрудники банка внесли несколько предложений:

1. Нужно, чтобы сотрудники кол-центра могли проконсультировать клиентов хотя бы по текущим ставкам банка. Для этого надо каким-то образом предоставить их системе доступ к ставкам по депозитам.
2. Есть риск, что кол-центр будет перегружен. Поэтому необходимо подключить к работе партнёрский кол-центр. При этом важно, чтобы сотрудники партнёрского кол-центра также могли проконсультировать клиентов по актуальным депозитным ставкам. Для этого нужно наладить процесс передачи информации об актуальных ставках между банком и кол-центром. Кол-центр партнёра работает во внешней информационной системе относительно банка. Они готовы получать актуальные ставки в виде файлов. Нет возможности сделать API-вызовы (например, через SFTP-протокол).
3. Все эти изменения необходимо учесть в MVP и предложить решение на основе текущего процесса работы со ставками.

### <a name="_qmphm5d6rvi3"></a>**Решение**

Для реализации нового требования по консультации клиентов через внутренний и партнёрский кол-центры выбран подход с максимальным переиспользованием уже предложенных в MVP компонентов цифрового контура открытия депозитов.

**Логика принятия решений**

1. Один источник актуальных ставок

    Было важно не допустить появления нескольких независимых источников ставок для цифровых каналов и кол-центров. Поэтому ставки продолжают вестись в банковском контуре, а наружу публикуется только read-модель.

2. Изоляция АБС от прямой нагрузки со стороны кол-центров

    Внутренний и партнёрский кол-центры не должны обращаться напрямую к АБС, так как она уже перегружена и является критичной core-системой. Это соответствует ранее зафиксированным ограничениям MVP.

3. **Переиспользование существующих компонентов MVP**

    Вместо введения новых сервисов выбран путь функционального расширения уже имеющихся компонентов:
    - Catalog API используется как единый API чтения ставок,
    - ABS Integration Adapter остаётся компонентом синхронизации ставок из АБС,
    - Call Center Integration Adapter расширяется для файловой выгрузки ставок партнёру.
4. **Учёт ограничений внешнего партнёра**

    Партнёрский кол-центр не готов использовать API и может получать данные только файлами. Поэтому для внешнего контура выбран пакетный файловый обмен.

5. **Совместимость с текущим технологическим ландшафтом**

    Для новых доработок используется тот же подход, что и в MVP: backend-логика цифрового контура строится на технологиях, близких к текущей внутренней экспертизе банка, без необходимости глубоко менять АБС или платформу кол-центра подрядчика.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

1. **Создать отдельный сервис публикации ставок для кол-центров**

    Можно было бы реализовать новый специализированный сервис, который отдельно публикует ставки во внутренний и партнёрский кол-центры. Такой подход лучше разделяет ответственность, но не был выбран, потому что для MVP важнее минимизировать число новых компонентов и переиспользовать уже существующие сервисы цифрового контура.

2. **Дать внутреннему кол-центру прямой доступ к Rates Read Model DB**

    Такой вариант уменьшает число сервисных вызовов и выглядит проще технически, но не был выбран, потому что БД становится интеграционным контрактом между системами. Это делает решение менее управляемым, ухудшает версионирование и увеличивает связанность.

3. **Организовать прямую интеграцию кол-центров с АБС**

    Внутренний и партнёрский кол-центры могли бы получать ставки напрямую из АБС. Такой подход не был выбран из-за рисков нагрузки на АБС, ограничений по доступности и нежелательности раскрытия внутреннего банковского контура наружу.

**Недостатки, ограничения, риски**

1. **У Call Center Integration Adapter расширяется зона ответственности**

    Теперь он отвечает не только за передачу заявок с сайта в систему кол-центра, но и за передачу ставок партнёру в файловом виде. Это упрощает состав системы на уровне MVP, но делает компонент более нагруженным по логике и потенциально менее чистым архитектурно.

2. **Появляется риск рассинхронизации между read-моделью ставок и фактически переданными файлами**

    Если файл для партнёра будет сформирован с задержкой или передача завершится ошибкой, партнёрский кол-центр может консультировать по устаревшим ставкам.

3. **Партнёрский файловый обмен остаётся ограничением решения**

    Отсутствие API и невозможность использовать более удобные способы интеграции делают процесс менее гибким, увеличивают зависимость от формата файла и требуют отдельного контроля версий и статусов передачи.

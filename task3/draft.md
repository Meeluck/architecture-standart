
## Use Case

| UC-01 | Новый клиент, Сайт                                                                           | Просмотр депозитов на сайте                               | 1. Клиент просматривает доступные предложения.                                                                                                                                                                                                      | Основание — функциональное требование **F1**: сайт должен отображать список доступных депозитов с актуальными ставками. Сценарий напрямую вытекает из этого требования.                                                                                                                                                                                                                               |
| UC-02 | Новый клиент, Сайт                                                                           | Подача заявки на депозит через сайт                       | 1. Клиент выбирает подходящий депозит на сайте. 2. Клиент вводит Ф. И. О. и номер телефона. 3. Сайт выполняет отправку заявки. 4. Заявка сохраняется и передаётся в дальнейшую обработку.                                                                                                                                                                      | Основание — функциональное требование **F2**: сайт должен позволять новому клиенту подать заявку на депозит, указав Ф. И. О. и номер телефона. Сценарий напрямую вытекает из требования.                                                                                                                                                                                                              |
| UC-03 | Оператор кол-центра, Система кол-центра, Сайт                                                | Обработка заявки с сайта в кол-центре                     | 1. Система кол-центра получает заявку, поданную с сайта. 2. Оператор кол-центра открывает заявку в своей системе. 3. Оператор связывается с клиентом. 4. Оператор уточняет параметры заявки и может предложить клиенту условия по депозиту.                                                                                                                    | Основание — функциональное требование **F3**: заявка, поданная с сайта, должна передаваться в систему кол-центра для дальнейшей обработки менеджером. Сценарий также согласуется с описанием целевого процесса, где после заявки клиенту звонит менеджер кол-центра и работает с заявкой в своей системе.                                                                                             |
| UC-04 | Сотрудник бэк-офиса депозитов, АБС, Система кол-центра                                       | Предварительная обработка заявки и определение ставки     | 1. Заявка, принятая через кол-центр, передаётся во внутренний контур банка. 2. Сотрудник бэк-офиса депозитов открывает заявку. 3. Сотрудник анализирует заявку и определяет ставку по депозиту. 4. Результат фиксируется во внутренней системе. 5. Информация становится доступной для дальнейшего взаимодействия с клиентом.                                  | Основание — функциональные требования **F8/F10**: на этапе MVP заявка должна обрабатываться менеджером бэк-офиса, а в банке должен быть реализован централизованный системный контур ведения ставок и согласования ставки по заявке. Дополнительно сценарий опирается на текущий процесс, где заявки из кол-центра заранее обрабатываются в АБС для определения ставки до визита клиента в отделение. |
| UC-05 | Новый клиент, Сотрудник фронт-офиса отделения                                                | Очная идентификация нового клиента в отделении            | 1. После обработки заявки и звонка клиент приходит в отделение банка. 2. Сотрудник фронт-офиса проводит идентификацию клиента по документам. 3. После успешной идентификации клиент может продолжить процесс открытия депозита.                                                                                                                                | Основание — не отдельное функциональное требование, а ограничение бизнес-процесса MVP: новый клиент после подачи заявки с сайта должен пройти очную идентификацию в отделении. Сценарий появился из описания целевого процесса и отражает границу цифровизации.                                                                                                                                       |
| UC-06 | Действующий клиент, Интернет-банк                                                            | Просмотр депозитов и персональных ставок в интернет-банке | 1. Клиент входит в интернет-банк. 2. Интернет-банк отображает список доступных депозитов. 3. Интернет-банк показывает общие и персонализированные ставки клиента. 4. Клиент выбирает подходящий продукт.                                                                                                                                                       | Основание — функциональное требование **F5**: интернет-банк должен отображать список доступных депозитов с актуальными и персонализированными ставками. Сценарий напрямую вытекает из требования.                                                                                                                                                                                                     |
| UC-07 | Действующий клиент, Интернет-банк                                                            | Подача заявки на открытие депозита через интернет-банк    | 1. Клиент выбирает депозитный продукт. 2. Клиент указывает счёт списания и сумму депозита. 3. Интернет-банк формирует заявку на открытие депозита. 4. Клиент инициирует отправку заявки.                                                                                                                                                                       | Основание — функциональное требование **F6**: интернет-банк должен позволять клиенту подать заявку на открытие депозита с указанием счёта и суммы депозита. Сценарий напрямую вытекает из требования.                                                                                                                                                                                                 |
| UC-08 | Действующий клиент, Интернет-банк, СМС-сервис                                                | Подтверждение заявки по СМС-коду                          | 1. После подачи заявки интернет-банк инициирует отправку СМС-кода клиенту. 2. Клиент получает код на телефон. 3. Клиент вводит код в интерфейсе интернет-банка. 4. Система проверяет корректность кода. 5. После успешной проверки заявка считается подтверждённой.                                                                                            | Основание — функциональное требование **F7**: подача заявки через интернет-банк должна подтверждаться СМС-кодом. Сценарий напрямую вытекает из требования.                                                                                                                                                                                                                                            |
| UC-09 | Сотрудник бэк-офиса депозитов, АБС                                                           | Обработка заявки менеджером бэк-офиса                     | 1. Сотрудник подтверждает или уточняет условия депозита. 5. Результат обработки фиксируется в АБС.                                                                                                             | Основание — функциональное требование **F8**: на этапе MVP заявка должна обрабатываться менеджером бэк-офиса, который подтверждает условия депозита в АБС. Сценарий напрямую вытекает из требования.                                                                                                                                                                                                  |
| UC-10 | Сотрудник бэк-офиса депозитов, Сотрудник бэк-офиса кредитов, АБС                             | Согласование специальной ставки                           | 1. В ходе обработки заявки определяется необходимость согласовать специальную ставку. 2. Сотрудник депозитного бэк-офиса инициирует запрос на согласование. 3. Итоговая ставка согласовывается и фиксируется в системе. | Основание — функциональные требования **F10/F11**: должен быть реализован централизованный системный контур ведения ставок и согласования ставки по заявке, а сотрудники депозитного и кредитного бэк-офиса должны иметь возможность работать с данными по ставкам. Дополнительно сценарий опирается на текущий процесс, где специальные ставки согласуются с участием кредитного подразделения.      |

При необходимости оформляются и сохраняются связанные данные и документы.                                                                                                        | Основание — функциональное требование **F8**: на этапе MVP заявка обрабатывается менеджером бэк-офиса, который подтверждает условия депозита в АБС. ## Нефункциональные требования

| Код | Требование| Комментарий / основание|
| --- | --- | --- |
| U   | Удобство использования (Usability) |              |
| U1  | Интерфейсы сайта и интернет-банка должны быть удобными для клиента|
| U2  | Интерфейсы должны соответствовать корпоративной дизайн-системе и использовать брендированные элементы  ||
| | | |
| R   | Надёжность (Reliability)           |              |
| R1  | Сервисы нового процесса должны работать в режиме 24/7 с целевой доступностью 99,9%| |
| R2  | Архитектура должна исключать ситуацию, при которой рост онлайн-заявок ставит под угрозу работоспособность АБС и банка в целом | |
| **R3**  | Недоступность или перегрузка АБС не должна блокировать приём заявок в цифровых каналах | Это архитектурно значимое обобщение, вытекающее из ограничения: «лучше избежать прямой работы интернет-банка с API АБС в новом процессе» и из перегруженности АБС. |
| | | |
| P   | Производительность (Performance)   |              |
| P1  | Отклик клиентских операций и загрузка справочных данных должны быть существенно быстрее текущего уровня, при котором часть данных загружается более секунды | |
| **P2**  | Архитектура должна поддерживать горизонтальное масштабирование клиентских сервисов и распределение запросов между серверами и ЦОД | Прямо следует из условия: «лучше предусмотреть равномерное горизонтальное масштабирование и распределение запросов между серверами, приложениями и ЦОД». |
| | | |
| S   | Поддерживаемость (Supportability)  |              |
| S1  | Решение должно по максимуму использовать уже существующие в банке технологии и платформы | |
| S2  | При выборе новых технологий они должны быть совместимы с существующими платформами разработки и поддерживаться имеющейся в банке экспертизой | |
| S3  | Для решения должна быть подготовлена документация, достаточная для последующего расширения системы | |
| | | |
| +R  | + Ограничения (Restrictions)       |              |
| +1  | Передача данных с сайта и из интернет-банка должна быть защищена механизмами шифрования трафика | |
| +2  | Для реализации SMS-подтверждения желательно не дорабатывать ядро интернет-банка силами подрядчика и по возможности реализовать функциональность силами команды банка | |
| +3  | Kafka допустимо использовать как перспективную технологию интеграции, но нужно учитывать несовместимость с текущей платформой интернет-банка | |
| +4  | Следует избегать прямой интеграции интернет-банка с API АБС в новом процессе | |
| **+5**  | АБС можно рассматривать только как вертикально масштабируемый компонент; требования по горизонтальному масштабированию на неё не распространяются |Прямо следует из условия: «АБС может масштабироваться только вертикально из-за своей базы данных». |
| **+6**  | Текущая инфраструктура интернет-банка не обеспечивает требуемую отказоустойчивость и должна рассматриваться как ограничение MVP | Прямо следует из условия: «Команда интернет-банка утверждает, что эти требования пока невыполнимы». |
| **+7**  | При проектировании нужно учитывать наличие основного и резервного ЦОД и возможность распределения нагрузки между ними в будущем | Прямо следует из условия: «У банка есть резервный ЦОД...» и «лучше предусмотреть ... распределение запросов ... между ... ЦОД». |
